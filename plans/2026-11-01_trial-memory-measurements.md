# VRAM and RAM Measurements for Trial Executions

## Problem Statement

A sweep answers "which configuration is fastest", but not "what will that configuration cost me on real hardware". The two are usually in tension: `gpu_memory_utilization`, KV-cache dtype, quantization, tensor parallelism, an offloaded MoE, a CPU-offload layer count, or a smaller batch size all move throughput and memory in opposite directions. Today the tool reports CPU-offload and cache tunables but never measures the memory they consume, so the user has to re-run a candidate configuration by hand, watch `nvidia-smi`/`rocm-smi` and the container's memory, and guess.

That is the exact decision a sweep is supposed to inform. Picking a point off the Pareto front requires knowing whether it fits the target GPU at all: a configuration that is 4 % faster but needs 6 GiB more VRAM is the wrong choice on the user's card. The same is true for RAM, where a CPU-offloaded MoE or a large context cache can require more system memory than the host has. Without measurements, the recommended configuration in the final summary comes with a throughput number and no statement about whether it can actually be deployed.

The data is available and cheap to obtain — the host already knows how to probe its accelerators, the container runtime already knows how to report a container's memory, and both vendor toolchains expose a per-second query that costs a fraction of a second — but the tool throws it away and never records it.

## Solution

Measure VRAM and RAM for every trial and record them as informational metadata alongside its throughput.

Two numbers are captured for each trial, each as a peak rather than an average, because a hardware requirement is a ceiling:

- the **lifetime peak**, over the server container's whole life — model load, health wait, warmup, and the measured runs; and
- the **measured peak**, over the windows of the measured benchmark runs only.

The lifetime peak is the headline "hardware requirement" of a configuration, because it includes the engine's one-off allocation at startup (vLLM sizes its KV cache from `gpu_memory_utilization` when it loads the model, and a llama.cpp server's mmap'd weights become resident early). The measured peak describes what the configuration holds while actually serving requests. Keeping both means a user can tell "this configuration needs 20 GiB to start, 17 GiB to serve" from "this configuration needs 20 GiB always".

VRAM is attributed to the trial itself: the sum of the VRAM of the GPU processes inside the container, matched by cgroup membership. Where that is unavailable, the measurement falls back to the device-level used-VRAM delta against a baseline taken before the container started, and records which of the two sources produced the number, so a value is never silently of a different kind than it appears.

RAM is the container's cgroup memory usage, sampled on the same cadence. It includes page cache, so a llama.cpp container's mmap'd weights count as RAM the configuration actually holds.

Measurement is always on, best-effort, and silent. It adds no flags, changes no objective, never affects scoring or pruning, and never fails or retries a trial: a host without vendor tooling, a runtime that cannot report stats, or an unreadable cgroup simply yields no number for that field. A CPU target has no VRAM but still reports RAM. The per-run numbers ride on the run metrics exactly like the engine-reported phase rates, the peaks are summarized on the trial result, persisted in the study's per-trial projection, and printed for the recommended configuration in the final summary:

```
best throughput: 51.37 tps
trials run: 24
failed trials: 1/24 (4%)
hardware: 20.4 GiB vram peak (measured 17.1 GiB), 6.2 GiB ram peak (measured 5.9 GiB)
```

Live output (the per-trial log line and the TUI) and the Pareto front table are unchanged; the new numbers are read from the study and from the final summary rather than crowding the live lines.

## User Stories

1. As a tuning user, I want each trial to record its peak VRAM usage, so that I know which of the configurations my GPU can actually hold.
2. As a tuning user, I want each trial to record its peak RAM usage, so that I know whether a CPU-offloaded or large-cache configuration fits my host.
3. As a tuning user, I want memory to be reported but never optimized, so that the sweep's result is still the fastest configuration rather than an invented memory/throughput blend.
4. As a tuning user choosing a point from the Pareto front, I want the memory of each candidate, so that I can weigh a small throughput gain against a large VRAM cost.
5. As a tuning user, I want the peak over the whole container lifetime, so that the number tells me the memory I must have free to *start* the configuration, not just to serve it.
6. As a tuning user, I want the peak over the measured runs separately, so that I can see how much of the lifetime peak is a startup allocation that might be reused.
7. As a tuning user, I want the recommended configuration's memory printed in the final summary, so that the file I take away comes with the hardware it needs.
8. As a tuning user with a vLLM deployment, I want VRAM measured while `gpu_memory_utilization` and the KV-cache settings vary, so that the sweep shows me the real cost of each setting instead of the fraction I typed.
9. As a tuning user with a llama.cpp deployment, I want RAM measured while `n_cpu_moe`, `n_gpu_layers`, and the cache tunables vary, so that I can find the offload point that still fits my machine.
10. As a tuning user on an NVIDIA host, I want VRAM taken from `nvidia-smi`, so that the measurement needs no engine cooperation and works with any image.
11. As a tuning user on an AMD host, I want VRAM taken from `rocm-smi`, so that the feature works on my platform and not only on CUDA.
12. As a tuning user on a shared GPU, I want the trial's own processes measured rather than the whole device, so that another workload on the same card does not inflate the numbers.
13. As a tuning user on a host where per-process attribution is unavailable, I want a device-level fallback, so that I still get an approximate number instead of nothing.
14. As a tuning user, I want the run's own record to say whether VRAM came from per-process attribution or a device-level fallback, so that I can judge how much to trust the number.
15. As a tuning user, I want an idle-GPU baseline recorded, so that I can subtract it myself and understand a device-level number that includes someone else's memory.
16. As a tuning user running a CPU-only sweep, I want RAM reported and VRAM absent, so that CPU deployments are covered without fabricating a GPU number.
17. As a tuning user, I want measurement to run automatically, so that I do not have to remember a flag or lose the data on a sweep I already ran.
18. As a tuning user, I want a host without vendor tooling to still complete its sweep, so that a missing `nvidia-smi` never costs me the run.
19. As a tuning user, I want no measurement to appear as `n/a` rather than `0`, so that "unmeasured" and "used nothing" are distinguishable.
20. As a tuning user, I want a failed probe to be silent, so that a diagnostic cannot become a wall of warnings in an unattended log.
21. As a tuning user resuming a stored study, I want the memory of earlier trials preserved, so that a resumed sweep still shows the footprint of the points it already evaluated.
22. As a tuning user, I want a study created before this feature to still load and resume, so that the added metadata never invalidates my existing work.
23. As a tuning user, I want the memory of a per-run repetition visible on the run, so that I can tell a stable footprint from one that varies between repetitions.
24. As a tuning user, I want the raw samples kept with the run, so that I can audit a suspicious measurement afterwards.
25. As a tuning user, I want the measurement cadence fast enough to catch a startup allocation, so that a peak that lasts a second or two is not missed.
26. As a tuning user, I want the sampler stopped with the container, so that a finished sweep leaves no background process polling my GPU.
27. As a tuning user interrupting a sweep, I want the sampler torn down with the container, so that an interrupt leaves nothing behind.
28. As a tuning user, I want memory recorded only for successful trials, so that a trial that never loaded the model does not report a meaningless peak.
29. As a tuning user, I want the live per-trial line and the TUI to keep their current shape, so that my existing log parsing and screen layout do not change.
30. As a tuning user, I want no extra command-line flags, so that nothing about my existing invocations changes.
31. As a tuning user reading the usage guide, I want the memory fields, their peak semantics, their sources, and their best-effort caveat documented, so that I know what the numbers mean.
32. As a developer, I want the memory numbers to live on the engine-neutral experiment surface, so that they are not tied to vLLM, llama.cpp, Podman, or a GPU vendor.
33. As a developer, I want the sampler injectable, so that the orchestrator, the client, and the tests never shell out to a real vendor tool.
34. As a developer, I want the vendor parsing confined to the hardware module, so that engine and runtime layers stay free of vendor vocabulary.
35. As a developer, I want container RAM read through the runtime handle, so that the memory logic is not duplicated per container backend.
36. As a developer, I want the two peaks computed from one sample series, so that they cannot disagree about what was observed.
37. As a developer, I want the new fields optional with a harmless default, so that every existing result construction keeps compiling and behaving.
38. As a developer, I want the persisted projection to carry plain integers, so that the study stays JSON-serializable and portable.
39. As a developer, I want the metric schema version untouched, so that this informational addition does not force a resume refusal.
40. As a developer, I want the summary to read the numbers from the recorded projection like the combined-throughput column does, so that the rendered summary and the persisted study cannot disagree.
41. As a developer, I want the memory measurement to reuse the existing best-effort contract of the metrics scrape, so that the two diagnostic channels behave the same way.
42. As a maintainer of the artifact writers, I want the new measurements to stay out of the generated configurations, so that no writer changes and no artifact gains fields a deployment would ignore.

## Implementation Decisions

- **Two peaks, one sample series.** A trial records two `ResourceUsage` values: the lifetime peak of the server container and the max over the measured runs' window peaks. Both are derived from one sampled series, so a run's peak can never exceed the trial's lifetime peak from a different observation basis.
- **Peak, not mean.** Unlike the phase rates, memory does not aggregate as a mean. The trial-level fields are maxima; a `ResourceUsage` documents itself as a peak so no consumer averages it by habit.
- **New engine-neutral value type.** `ResourceUsage` is a frozen, hashable engine-neutral type on the experiment surface with two optional integer fields, `peak_vram_bytes` and `peak_ram_bytes`. Absence is `None`, never `0`.
- **Attachment points.** `RunMetrics` gains an optional `resources` field holding that measured run's window peak; `ExperimentResult` gains `lifetime_resources` holding the whole-container peak and a derived `measured_peak_resources` property that takes the element-wise maximum over the runs' `resources`. The derived property follows the existing invariant that runs are the single source of truth for the trial aggregate.
- **Backwards compatibility.** `lifetime_resources` defaults to an all-`None` `ResourceUsage`, so every existing result construction, test fixture, and legacy persisted study keeps working without modification. Hashing is extended on both `RunMetrics` and `ExperimentResult`.
- **`ResourceSampler` protocol.** The experiment surface declares a small protocol with an opaque window marker (`mark()`), a window peak query (`peak(since)`), and a lifetime peak accessor. Consumers treat the marker as opaque, so the client learns nothing about where numbers come from.
- **Sampler implementation.** A background-thread sampler, owned by the orchestrator and spanning `start_container` → `stop`, appends timestamped samples on a fixed one-second cadence and answers window and lifetime queries from them. Its RAM reader and VRAM probe, its clock, and its sleep are injected, so tests drive it without a daemon, a GPU, or real time. It is engine-neutral and lives with the host measurement layer, not with a backend.
- **Container RAM source.** The runtime's running-container handle gains a best-effort `memory_usage()` that reports the container's cgroup memory in bytes, including page cache. Any runtime or API failure reports "unknown" rather than raising. This keeps container-memory knowledge in the runtime layer, which stays engine-free.
- **VRAM source.** The hardware module gains a memory probe selection for the detected target, alongside its existing device-count probes: NVIDIA through `nvidia-smi`, AMD through `rocm-smi`, none for a CPU target. Each probe returns the device's used memory and a per-process mapping, parsed by pure functions over captured tool output.
- **Attribution rule.** VRAM is the sum of the per-process values whose process cgroup names the container's id. When no process can be attributed, the value is the device's used memory minus a baseline captured before the container was created, clamped at zero. The sample records which source was used, and the baseline is kept with the run so the device-level number stays interpretable.
- **Sampling window.** The baseline is taken before the container starts; sampling starts immediately after it is started, so the model-load phase is covered; sampling stops when the container is stopped, including on the failure and interrupt paths, so nothing polls the host after a trial ends.
- **Client seam.** The host benchmark client accepts an optional sampler and brackets each measured run window with a marker and a peak query, storing the returned `ResourceUsage` on the run through a helper that mirrors the existing metrics-snapshot helper. Warmup runs are not bracketed, because the lifetime peak already covers them and they are deliberately unmeasured.
- **Per-run raw data.** Each run's raw payload keeps the bracketing samples (values, timestamps, and the VRAM source) and the baseline, so a run's number can be audited without re-running anything. The existing metrics-snapshot key and the engine payloads are untouched.
- **Persisted projection.** The trial projection recorded under the result user attribute gains the lifetime peaks and, per run, that run's peaks, all as plain integers or `null`. No metric-schema bump and no resume rule: the addition is optional metadata that does not reinterpret any existing score.
- **Final summary.** The summary prints one hardware line for the recommended configuration, carrying the lifetime and measured peaks, formatted by a new byte-size helper beside the existing duration and failure helpers. The line is rendered in both scalar and multi-objective modes, and each field renders `n/a` when it was not measured. The numbers are read from the recommended trial's recorded projection, the same source the front table's combined column uses, so the summary cannot contradict the study.
- **Live output unchanged.** The per-trial log line, the TUI graph and status line, the Pareto front table, the startup header, and the generated configuration artifacts are unchanged.
- **No CLI surface.** Measurement is always on; no flag, environment variable, or configuration key is added, and nothing about the experiment config types changes.
- **Documentation.** The usage guide gains a memory-footprint note with a sample summary line, the peak semantics, both sources, the baseline, the best-effort caveat, and the CPU-target rule; the architecture guide gains the sampler seam in its data flow; the repository guidelines gain the invariant that memory measurement is best-effort, engine-neutral, objective-free, and outside the metric schema.

## Testing Decisions

Good tests here assert externally observable values and lifecycle effects, not internal plumbing: the resource usage a run or a result carries, the sampled peaks a fake probe produces, the parsed numbers from captured vendor output, the absence of a measurement, and the rendered summary line. Tests must not assert private thread state, cadence counters, or exact subprocess argv beyond what the documented contract requires.

- **Value type and aggregation**: assert that a run's resources round-trip through the run, that the trial's measured peak is the element-wise maximum over the runs, that a missing measurement yields `None` rather than zero, that a result built without a lifetime usage still round-trips, and that hashing is stable. Prior art: the existing engine-neutral type tests.
- **Runtime memory usage**: assert the byte count from a fake container stats response, and that an API failure, a malformed payload, or a missing field reports unknown instead of raising. Prior art: the fake-client runtime tests, which already assert best-effort behavior for logs and liveness.
- **Vendor VRAM parsing and attribution**: assert parsed device and per-process values from captured `nvidia-smi` and `rocm-smi` output, CPU target selection, and that attribution prefers in-container processes and falls back to the baseline-clamped device value. Prior art: the existing hardware-detection tests, which inject probes and assert target and device count.
- **Sampler**: assert window peaks over an injected clock and sample source, the lifetime peak, that a window with no samples reports unknown, that a failed probe yields unknown, and that stopping the sampler ends sampling. No sleeping and no real subprocesses.
- **Client seam**: assert that measured runs carry a window peak, that warmup runs carry none, that a sampler-less client behaves exactly as before, and that a run whose sampler answers nothing still produces a valid run. Prior art: the existing client tests with a fake transport and clock.
- **Orchestrator lifecycle**: assert that the sampler is started after the container and stopped before the result is returned, that the lifetime peak reaches the result's aggregate field, that the tokenizer preflight is not sampled, and that a failed measurement still stops the sampler. Prior art: the orchestrator tests with fake container and benchmark clients.
- **Persisted projection**: assert the projection carries the lifetime and per-run peaks and tolerates absent ones, keeping the payload JSON-serializable. Prior art: the existing projection/optimizer tests.
- **Summary rendering**: assert the hardware line in scalar and multi mode for fully measured, partially measured, and entirely unmeasured results, plus the byte-size formatting boundaries. Prior art: the pinned-string summary tests and the shared formatting tests.
- **Prior art**: follow the project's convention of injecting probes, clocks, and clients so unit tests need no daemon, no GPU, and no vendor tooling, and of asserting rendered strings for reporters.
- **Integration coverage for the two measurement seams.** The default suite stays hermetic, but two seams are only observable against the real thing: the runtime handle's `memory_usage()` against a live Podman container, and the vendor memory probes against the installed `nvidia-smi`/`rocm-smi`. Both get `integration`-marked tests in the existing style — each locates its prerequisite at test time and skips when it is missing, so a daemon-less, GPU-less, or partially tooled host stays runnable. They assert the seam's own contract (a plausible cgroup figure above a known allocation, a live vendor answer that parses), not the trial-level peaks, which the hermetic tests already pin from injected samples.

## Out of Scope

- Making memory an objective, a constraint, a penalty, a pruner, or a filter: a configuration that does not fit is still evaluated and still scored on throughput.
- Rejecting or warning about a configuration that exceeds an available-memory budget, and computing headroom against the device's total memory or the container's configured memory limit.
- Adding the numbers to the live per-trial log line, the TUI graph or status line, the Pareto front table, the startup header, or the written configuration artifacts.
- New command-line flags, environment variables, or configuration keys to enable, disable, or tune the measurement.
- Measuring from engine-reported metrics; the engine's own exposition is used only for phase rates as today.
- Measuring host-wide memory, per-device totals, GPU utilization, temperature, or power.
- Attributing memory across multiple devices per trial, or reporting a per-device breakdown.
- Recording memory for failed trials, or measuring during the dataset-tokenizer preflight.
- Persisting the full sample series in the study; only the peaks and the per-run raw payload survive.
- Changing the metric schema version, adding a resume rule for memory, or backfilling measurements into a study recorded before this feature.
- Changing how the sampler cadence, the probe timeouts, or the container lifetime are configured.
- Platforms or runtimes that cannot report container stats at all, beyond leaving the RAM field absent.

## Further Notes

- One-second sampling is the accuracy/overhead compromise: a vendor query costs a fraction of a second on both toolchains (measured locally at roughly 0.2 s for `rocm-smi`), and the peaks that matter are allocations the engine holds, not fleeting transients. A sub-cadence spike can be missed; the documentation says so rather than implying a profiler's accuracy.
- The cgroup memory figure deliberately includes page cache. For an mmap-based llama.cpp server the weights are file-backed pages that the kernel may reclaim, so treating them as RAM is conservative in the direction a hardware requirement should be: it never understates.
- Device-level fallback values include whatever else uses the GPU. Recording the baseline and the source next to the peak is what makes such a number honestly interpretable, and per-process attribution is what makes the common case exact; on a shared card the two will differ, and the difference is informative rather than a bug.
- The measured-run peak is a maximum of per-run peaks, not a peak over the union of the run windows. Windows are adjacent but the gaps between them are unscraped, so a maximum of maxima is exact where a shared scan would not be.
- Adding defaulted fields keeps every existing result construction valid, which matters because results are built by both backends, by the orchestrator, and by a dozen test fixtures; the alternative (a required field) would have forced edits across the tree with no behavioral benefit.
- The trial projection is the only persistence surface, so the numbers survive a resume and are visible to anyone who inspects the study, without introducing a second storage format or a study attribute of its own.
- The feature adds no engine code: neither backend learns about memory, so a third engine gets the measurements for free as long as it plans a normal server container.
- The two integration tests exist because each seam's real counterpart has a shape no fake can guarantee: a Podman stats payload and a vendor tool's live output. Both seams are best-effort by design, so neither test may fail an otherwise healthy run — the skip is the honest outcome when the prerequisite is absent, and a divergence in either counterpart surfaces as a failure only where that counterpart actually reported something.
- **Amendment (follow-up to T8): the summary's subjects are split.** The hardware line reported the recommended trial's peaks, which left "what did this sweep reach" and "what does the configuration I take away need" answered by one number. The line now reports the largest peak *any* evaluated trial recorded, read as a maximum over the study's per-trial projections, and the winning-configuration section opens with a `memory` subsection reporting the recommended configuration's own lifetime and measured peaks. Nesting it there means a footprint can never be printed without the configuration it describes, and the subsection is omitted entirely when the recommended trial measured nothing, so a legacy study prints its configuration alone. Both remain informational, a partially measured trial still renders the missing field as `n/a`, and neither reads anything the projection does not already carry — so no study format, metric schema, or scoring behaviour changes.
